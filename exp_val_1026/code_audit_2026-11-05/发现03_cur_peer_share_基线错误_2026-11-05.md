# 发现 ③：`drift_cur_share` 低于"随机基线"是口径 bug，不是图的问题

**日期**：2026-11-05
**触发**：校准跑（ρ=0.20 / 0.80）里 `drift_cur_share` = 0.1411 / 0.1229，
而 `drift_cur_base` = 0.2003 —— 邻居比随机抽的用户还更不可能同兴趣，看起来像是
"修好冻结之后图仍然不跟踪当前兴趣"。**结论：这是指标口径错误，修正后方向相反。**

---

## 1. 指标现在的算法（`val02_run_ema.py::CohortEdgeProbe.probe`）

```python
match_cur = ((dom == user_dom) & (user_dom >= 0) & (dom >= 0)).float()   # 邻居是否同主类别
cur_share = (match_cur.gather(1, nbr) * w).sum(1) / w.sum(1)             # ← 加权、无条件
cur_base  = freq[user_dom.clamp_min(0)]                                  # ← 条件在"邻居有类别"上
```

两者的**样本空间不一致**：

| 量 | 分母里包含什么 |
|---|---|
| `cur_share` | 所有邻居，**包括主类别未知（dom=-1）的邻居**，它们被算成"不匹配" |
| `cur_base` | 只按"该类别在**有效用户**中的频率"算，隐含假设**邻居一定有类别** |

而实际上，任一窗口里有交互、因而有主类别的用户只占 **24%–30%**：

```
W1 1429/6040 = 23.7%   W2 23.9%   W3 29.7%   W4 26.2%   W5 29.5%
```

所以 `cur_base` 高了约 **1/0.295 ≈ 3.4 倍**。

## 2. 算术验证（决定性）

在 W5 的评测人群上（drift 组，105 人有有效主类别）：

```
代码给的 base（= 有效用户内的类别频率）       0.1936
该窗口有类别用户的占比                        1783/6040 = 0.2952
按同口径修正后的随机基线 = 0.1936 × 0.2952    0.0571
经验随机邻居基线（300 次重抽，K=20，同口径）   0.0564 ± 0.0049     ← 两者差 1.3%
```

**0.1936 × 0.295 = 0.0571 ≈ 实测 0.0564**，误差 1.3%。根因确认无疑。

## 3. 修正后的结论（方向反转）

| | share | 正确随机基线 | lift |
|---|---|---|---|
| ρ = 0.20 | 0.1411 | 0.0564 | **2.50 倍** |
| ρ = 0.80 | 0.1229 | 0.0564 | **2.18 倍** |

也就是：**图的邻居比随机邻居高 2.2–2.5 倍，图确实在跟踪当前兴趣**；
而且 ρ 越小 lift 越大（2.50 > 2.18），方向符合"低 EMA = 更灵敏"的预期。
之前"低于随机"的表象完全来自那个错配的 base。

## 4. 附带查出的两个更基础的事实

**（a）时间窗口是"等交互数"，不是"等时长"。** 5 个窗口各 199922 条交互，但时间跨度极不均匀：

```
p0   2000-04-25
p20  2000-07-21
p40  2000-08-29
p60  2000-11-20
p80  2000-12-02      ← W1–W4 全在这 8 个月里
p100 2003-02-28      ← W5 独占 26 个月
```

所以"跨一个窗口"在 W1→W2 是 1 个月，在 W4→W5 是 26 个月。
任何"兴趣漂移速度 / 恢复轮数"的解读都必须把这个时间不均匀性写进去，
否则"漂移得快/慢"可能是窗口宽度差异造成的。

**（b）每个窗口只有 24%–30% 的用户有交互。**
因为用户评分集中在很短的时间里（MovieLens 的会话式评分），
而窗口边界是全数据集的时间分位。后果：早期窗口里被抽样的客户端只有
**25%–46%** 有可训练数据（校准跑里 `trained 152–280 / 604`），
**实际参与率显著低于名义 C=0.1**。这一点旧实现也存在，但写报告必须交代。

## 5. 修法

`cur_peer_base` 改成**同口径**的随机基线（解析式即可，无需采样）：

```python
valid_frac = float((dom >= 0).mean())            # 该窗口"有类别用户"的占比
result["cur_peer_base"][member] = (freq[user_dom.clamp_min(0)] * valid_frac).cpu()
```

并建议同时：
* `cur_peer_share` 只在 `user_dom >= 0` 的用户上取均值（现在是给 dom=-1 的用户记 0，
  早期窗口里这类用户占 cohort 的 80%，会把均值拉塌）；
* 直接输出 `lift = share / base`，报告里只讲 lift（无量纲、可跨窗口比较）。

`val03_run_scenario.py` 目前没有这个指标，但它同样有"cohort 用户某窗口无交互"的问题
（`GroupProbe` 的 old/new peer share 用的是边界类别而非窗口类别，受影响方式不同，
需要单独核对一遍）。
