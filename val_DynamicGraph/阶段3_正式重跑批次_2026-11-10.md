## 4. 单轮耗时与墙钟外推

`onboarding` 的单轮耗时随「已上图用户数」增长：W1 只有 1429 个评估用户，W3 起 6040 个用户全部有边，邻居聚合成本随之上升（`1.6 s → 7.2 s`）。这不是退化，是**覆盖变全**的直接代价——正好是阶段 5 要写进报告的那件事。

| 臂 | 典型单轮 | 600 轮/run 估计 | 说明 |
|---|---|---|---|
| nograph | ~2 s | ~20 min | 无图分支 |
| static / static_at120 / static_build120 | ~2–7 s | 20–60 min | 冻结后不再更新图上 |
| periodic / periodic_boundary | ~7–9 s | 60–90 min | 每次都重建，重建后一轮最贵 |
| dynamic / onboarding / fresh_only | ~7–9 s | 60–90 min | 覆盖越全越贵 |

4 并发、加上共享 GPU 的干扰，**整批 ≈ 25–40 h**（128 run ÷ 4 × 40–75 min）。比 §7 表里的 7–8 h 高，原因是：①5 种子 + 冻结网格把 run 数从 84 提到 128；②共享 GPU 上的另一个作业占用了一半算力。墙钟不影响任何数值结论，只影响等待时间。

## 7. 风险与处置

| 风险 | 处置 |
|---|---|
| 单个 run 段错误（曾出现过一次解释器级崩溃） | `dg_run_formal_retry.sh` 最多 3 轮，按 `dg_summary.csv` 跳过已完成、只补缺 |
| 共享 GPU 上的作业抢算力，墙钟变长 | 不动别人的任务；只调整我们自己的并发（已是实测最优点 2/卡） |
| 崩溃后重排导致进程挤在同一张卡 | `dg_run_parallel.sh` 的 `pick_gpu` 按「自己进程数」选卡，并用 `kill -0` 剪枝 |
| 误覆盖 legacy 结果 | 全部写 `raw_formal` / `logs_formal` / `agg_formal`；legacy 目录只读 |
| 聚合/诊断脚本对新臂不适应 | 阶段 4 之前用 legacy raw 做过端到端预演（`_dryrun_phase4.sh`：聚合→冻结→质量→genre→报告→统计全通） |
