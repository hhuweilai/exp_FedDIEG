## 4. 实测墙钟（128 个 run 的真实数据）

| 项 | 数值 |
|---|---|
| 累计 GPU 时长 | **90.9 h**（`elapsed_seconds` 求和） |
| 墙钟 | **29.4 h**（4 并发） |
| 单 run 中位数 | ML ≈ **30 min**；Amazon ≈ **62 min**（Amazon 用户数 12381 = ML 的 2 倍） |
| 并发效率 | 90.9 / (29.4 × 4) ≈ **77%**（两张卡上还有别人的 1 个进程在分时） |
| 崩溃 | **1 次**解释器级段错误（`Segmentation fault`），由第 2 轮补跑自动完成；其余 127 个 run 一次成功 |

比 §7 表里的 16–20 h 长，原因是 Amazon 的 run 是 ML 的两倍长（用户数、图规模更大），
而估算时按「平均 30–36 min」算的；并发本身没问题（77% 已经接近这种单核串行负载的上限）。

**规模效应**（同一个 run 内部，不是退化）：`onboarding` 的单轮耗时随「已上图用户数」增长——
W1 只有 1429 个评估用户时约 1.6 s/轮，W3 起 6040 个用户全部有边时约 7.2 s/轮。
覆盖变全的直接代价就是变慢，这正好是阶段 5 要写进报告的那件事。

## 6. 与阶段 2 记录层的衔接

本批次全部 run 都带：

- `ecr_def = v2_empty_to_full`（F5 定义，旧 raw 的 `ecr` 是 legacy 定义，**不可与新数据混比**）
- `dg_graph_round_metrics.csv`：逐轮 `ecr_round_mean` / `added_round_sum` / `graph_turnover` / `active_coverage` / `is_update` / `is_refresh`
- `dg_user_coverage.csv`：逐用户 `first_covered_round`（C6）
- `core_version = 2026.11.08b`（F7/F8 后的版本号）

只要 `dg_verify_formal.sh` §4.1 的 `ecr_def` / `core_version` 唯一性检查通过，就能保证正式表里没有混进修复前的 run。

### 6.1 一个必须在报告里写清的口径（阶段 3 冒烟时发现）

`dg_summary.csv` 里有两个 ECR：

| 列 | 定义 | 对「非每轮更新」的臂 |
|---|---|---|
| `avg_ecr` | **评测点**那一轮的即时应变率（`gstats.ecr.mean()`） | ❌ 大多是 0：periodic_boundary 在 r21/141/261/381/501 更新，评测点在 10/20/30…，两者错开，评测点那轮没有更新 ⇒ 记 0 |
| `ecr_update_mean`（聚合表） | **真的更新了的轮次**上的 `ecr_round_mean` 均值 | ✅ periodic_boundary 实测 = **1.0**（5 个刷新轮，v2 定义：空→非空记 1） |

所以正式表**一律用 `ecr_update_mean`**（或 `dg_graph_round_metrics.csv` 的 `ecr_since_eval`），`avg_ecr` 只对「每轮都更新」的 dynamic 有意义。这就是 C1（ECR 记录时点）修好之后才看得出来的差别——旧的 `avg_ecr` 会让 periodic 看起来「图没变」，而 `graph_turnover`（0.90–0.98）说明重建其实换掉了几乎全部邻居。
