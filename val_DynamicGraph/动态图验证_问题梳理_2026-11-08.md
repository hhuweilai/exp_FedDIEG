## 3. 归因类问题（A）

### 3.1 A1：`dynamic−static` 的差值里混着「覆盖」——不能全部归因于动态演化

**原文表述**：StaticGraph 只覆盖部分早期用户、DynamicGraph 逐渐覆盖所有用户，所以两者差异不一定来自已有用户关系的动态调整。

**核实：成立。** 结果如下（seed 42，评测轮上的「有边用户数」）：

| ML-1M 轮次 | 30 | 60 | 120 | 150 | 250 | 390 | 510 | 600 |
|---|---|---|---|---|---|---|---|---|
| static（第 21 轮冻结） | 1264 | 1264 | 1264 | 1264 | 1264 | 1264 | 1264 | **1264** |
| static_at120 | 1366 | 1426 | 1429 | 1429 | 1429 | 1429 | 1429 | **1429** |
| periodic（每 120 轮重建） | 1264 | 1264 | 1264 | 2525 | 2525 | 5261 | 5972 | **5972** |
| dynamic（每轮 EMA） | 1366 | 1426 | 1429 | 2615 | 3599 | 5345 | 6013 | **6040** |

Amazon-Digital-Music 同型：static 冻结在 **2906**，periodic 阶梯 2906 → 6010 → 8542 → 10626 → 12237，dynamic 平滑涨到 **12381**。

**机制（已核到代码）**：

1. `feddieg_core/data.py` 用 `window_mode="slice"`，**每个窗口有自己的活跃用户集**；
2. `FedTrainer.train_round` 只让 `window.has_data(user)` 的客户端训练并上传摘要（`federated.py:213-214`），所以**用户只有在"自己活跃的那个窗口"里才可能进入摘要库**；
3. `graph.update` 的 `update_scope="all"` 只保证"每轮重算全部**已上传**节点"，**不能让没上传的人凭空获得邻居**；
4. 于是 dynamic 的覆盖平台随窗口推进逐级抬升：**1429 → 2664 → 4080 → 5400 → 6040**，**覆盖跳变全部发生在窗口边界（r130 / r250 / r370 / r490）**，窗口内几乎不动。这与「第 1..w 个窗口活跃用户的并集」在数量上完全吻合（机制推断；精确核对方式：拿 `window.active_users` 与「有边用户集合」做差集，应为空）。

**结论**：`dynamic − static` = (①后来窗口的新用户首次获得邻居) + (②已覆盖用户的关系持续重估)。当前实验只证明了这两项之和，**无法把 ② 单独测出来**。

**处置**：A4（onboarding）做臂级分解；A6（`active_coverage`）做机制级证据；A1 只改报告文字直到 A4 落地。

### 3.2 A2：periodic「5 次刷新」的解读要精确到「覆盖 + 时点」

**核实**：

- 刷新轮次 = `(r − 20 − 1) % 120 == 0` → **21 / 141 / 261 / 381 / 501**，共 5 次（`dg_common.py:237-238`，`period=120` 默认）。
- 数值：`periodic−nograph` ML **+0.0051**（95%CI [+0.0027, +0.0076]，窗口正号 100%，3/3 种子）；AZ **+0.0142**（[+0.0119, +0.0163]，3/3）。占总收益 67% / 82%。
- 每轮 EMA 相对它的额外边际只有 **+0.0025 / +0.0031**（33% / 18%）。

**新发现（原报告没有说清的一点）**：periodic 的**覆盖几乎追平 dynamic**——刷新之后同一轮对比达 **96%–99%**（r150 2525 vs 2615；r270 3938 vs 4026；r390 5261 vs 5345；r510 5972 vs 6013）。原因是每次重建会清空并按**当下全部摘要**重算，等于把"从上次刷新到现在所有新上传的用户"一次性补上。**所以 ④ 的收益不是来自"更新频率"（5 次 vs 580 次），而是来自"每次重建把此前所有新用户一次性补齐"——即覆盖。**

**还有一条原报告没提的对称事实**：`periodic` 在**窗口 1 与 static 完全相同**（r120 都是 1264，因为 W1 只有 r21 那一次建图），差异从窗口 2 起才出现——这与报告逐窗口表里"W1 四臂几乎相等（0.2256/0.2264/0.2264/0.2260）"完全吻合，是"重建=补覆盖"最直接的旁证。

**但 periodic 有 20 轮盲区**：刷新落在窗口开始后第 20 轮（21/141/…），所以在 r130（窗口 2 第 10 轮）periodic 仍是 1264，而 dynamic 已到 2221——**每个窗口的前 20 轮，periodic 对"本窗口新用户"完全没有邻居**。这正好是 ⑤（dynamic−periodic = +0.0025/+0.0031）最可能的来源：dynamic 靠每轮更新**提前 10–20 轮**覆盖新用户。

**参数化这条盲区**（实测）：r141 那次重建让覆盖从 1264 跳到 2525，即补进 **1261 名新用户**（≈63 人/轮 × 20 轮）；若改成在 r121 重建，只能补进约 **60 名**——**覆盖差一个数量级**。所以"20 轮偏移"不是随手取的，它恰恰是为了攒够新用户再重建。

**因此「更少、更有针对性的更新」的正确候选不是"窗口边界刷新"**：它会让覆盖大幅变差。真正有前途的"针对性"是**逐用户在其初次出现时建边**（A4）或**只更新有新证据的用户**（A5），它们既没有盲区，也不需要全局重建。

**处置**：

- A2 保留 `period` 扫描（20 / 120 / 240），但定位改为"频率—性能曲线"，并**明确预期**：更长的 period 会因盲区变大而更差，而不是更好；
- 新增可选的"相位诊断"：`--refresh-phase boundary`（r121/241/…）只跑 ML 3 种子，**预期更差**——它的价值是证明"20 轮偏移是承重的"，而不是候选方案；
- 真正的"更有针对性"由 A4/A5 回答。

### 3.3 A3：`static_at120` 语义 + 新增「真正第 120 轮建图」的臂

**原文表述**：static_at120 实际是第 21–120 轮持续更新后再冻结，不是第 120 轮才构图一次，需要改名或调整实现。

**核实：成立。** `dg_common.py:235-236` 的 `should_update` 为 `r <= freeze_round`，所以第 21–120 轮**每轮都更新**；`graph_updates=100`。覆盖轨迹 1366 → 1429 也证明它是"边更新边覆盖"。

**你的选择（§11 #1）是「改实现」**。落地方式（低风险版）：

- **保留** `static_at120` 目录与实现不动（它的语义就是"更新到 120 轮再冻结"），在报告/表中把它的名字解释清楚，回答的是"**晚冻结**是否比早冻结好"（现有 ①b = +0.0001）；
- **新增** `static_build120`：第 21–120 轮**完全不更新**，第 120 轮清空重建一次后冻结，回答"**晚建图**是否比早建图好"。

**为什么不直接改旧臂的名字/实现**：`dg_aggregate.py` 读的是 CSV 里的 `arm_dir` 列，不是目录名；只改目录名会让目录名与 CSV 内容不一致（对照对不上、图例错位）。要改名就必须重写 4 个 CSV 的列，代价和风险都比重跑 3 个 run 高。所以用"新增臂"实现"改实现"。

**必须预置分析口径（否则会误读）**：`static_build120` 在窗口 1 **没有任何图**（第 1–119 轮不建图：窗口 1 的评测点 10–110 全部无图，只有 r120 这一个评测点有图）。因此它的**整体窗口平均会被窗口 1 稀释**，不能与 `static` / `static_at120` 的平均值直接比。预先规定：①b2 的对比**只在窗口 2–5 上做**（并额外报告窗口 1 的"无图"证据，作为断言）；窗口 1 单独说明。

**另**：`static_at120` **只在 ML-1M 上跑过**（Amazon 8 个臂里没有），所以 `dg_report.py` 的 ①b 行在 Amazon 显示「没有对应结果」。若要在两个数据集上都谈"建图/冻结时点"，需补 Amazon 的 `static_build120`（+5 run）。

### 3.4 A4：`OnboardingOnlyGraph` 的规格

**目的**：把「新用户首次获得邻居」（覆盖）与「已覆盖用户的邻居持续重估」（演化）分开：

```
③ dynamic − nograph  =  ① static − nograph          （有图 vs 无图）
                     +  (onboarding − static)         （新用户覆盖的收益）
                     +  (dynamic − onboarding)        （已覆盖用户关系持续演化的收益）
```

**定义（按你的选择 #4）**：从第 21 轮起，每一轮对**当前还没有任何邻居行**的用户建一次边（用其"首次可用摘要"，即首次上传后的那一轮图更新）；一旦某用户有了邻居，其邻居集合与边权**不再更新**。其余协议（训练、FedAvg、评测、参与序列、负样本流）与动态臂完全一致。

**实现钩子（最小改动，不动 `feddieg_core`）**：

- `dg_common.py`：`ARM_CHOICES` / `ARM_LABELS` / `ARM_SHORT` / `arm_dir_name` 增加 `onboarding`；
- `PolicyGraph.update`：把 `update_users` 过滤成 `mask.sum(dim=1)==0` 的行，其余逻辑走基类；`graph_update_scope` 必须保持 `"all"`；
- `n_updates` 语义改为「至少有一个用户首次建边的轮数」；`dg_aggregate.py` 的 hygiene「预热后每轮都更新」只对 `dynamic` 生效（需确认 `onboarding` 不被误判）。

**必须写明的两个成分**（否则分解式会被读过头）：

1. 对第 21 轮前已上传的用户，onboarding 与 static **完全同构**（都在 r21 建边后冻结，图状态逐位相同）；
2. 对第 21 轮之后才出现的用户，其边只能在"出现时"用当时的摘要池建 ⇒ `(onboarding−static)` 的差值**只由这批晚出现用户贡献**，天然度量"晚出现用户是否被覆盖（含覆盖时点）"，而不是"有没有边"的二元效应。报告里写"覆盖（含时点）"，不要写"纯覆盖"。

**这个设计还有一个比 periodic 更强的性质**：onboarding 与 dynamic 对同一个用户的"首次建边轮次"**完全相同**（都在首次上传后的那一轮图更新，且新边初值同为 `(1−ρ)Δe`）；两者只差"之后要不要继续更新"。所以 `dynamic − onboarding` 是**纯演化效应**，不含任何覆盖时点差异——这正是只用 static/periodic 做不到的。

**验收断言**（加进 `dg_selfcheck.py` / `dg_hygiene.csv`）：

1. NoGraph 的 `delta_rel_max` 仍恒为 0；
2. onboarding 用户**建边后签名逐位不变**（逐用户记录首次建边轮次）；
3. onboarding 的最终覆盖 ≈ dynamic（ML 应达 6040；显著更低即说明扫描逻辑有漏洞）；
4. 同一 (数据集, 种子) 下各臂负样本流、评测用户、参与序列仍逐位相同；
5. **分解式自检**：逐种子核对 `① + (onboarding−static) + (dynamic−onboarding) == ③`（误差 ≤1e-12）——同一条恒等式也顺带证明 5 条臂共享同一参与序列与负样本流。

| 结果 | 含义 |
|---|---|
| onboarding ≈ dynamic | ② 的收益几乎全部来自**覆盖/时点**，「每轮 EMA」可省 → 第二阶段应做"谁来建边、何时建边"，不是 ρ 自适应 |
| dynamic > onboarding 且差距 ≈ ⑤ | 关系演化的真实价值 = 现有 ⑤ 的边际 → 与 periodic 结论互证 |
| onboarding ≈ static | 覆盖不是主因 → 需要重新归因 |

### 3.5 A5：`fresh_only`——「只更新有新证据的用户」

**目的**：直接回答原文问题 2 的"更有针对性的更新能不能打平"。

**定义**：每轮只对「自上次边更新后有过新上传」的用户重算邻居（`trainer.last_upload_round > 图上记录的该用户上次更新轮次`），其余用户保持旧边。`graph_update_scope` 仍为 `"all"`（扫描全部用户，但只更新有变化的）。

**实现钩子**：`PolicyGraph` 增加逐用户 `last_user_update`（int64 张量）；`dg_run.py` 在调用 `graph.update` 前用 `trainer.last_upload_round` 过滤 `update_users`。不改基类、不改训练。

**与其它臂的关系**：`fresh_only` = onboarding 的"持续版"（活跃用户持续更新）+ static 的"静止版"（不再活跃的用户冻结）。所以它同时检验两件事：不更新旧用户是否损失、少更新是否够用。

**风险（需在报告里预置）**：对"自己不再上传但邻居仍在变"的用户，`fresh_only` 的边会一直陈旧；若这部分用户占比高，`fresh_only` 可能明显差于 dynamic，这本身就是有价值的结论（说明"用户自己没新证据"不等于"关系不该更新"）。

### 3.6 A6：`active_coverage`——把"覆盖"从全局计数变成"本窗口有效覆盖"

**为什么必须加**：`graph_n_edges` 是**全局**有边用户数，而某个窗口的 NDCG 只取决于**该窗口被评测的用户**有没有邻居。现有 96%–99% 的"追平"是全局口径，可能掩盖"本窗口新用户仍缺边"。要精确验证 §3.2 的盲区假设，必须记录每个评测点上：

```
active_coverage = (本窗口被评测用户中已有邻居的人数) / (本窗口被评测用户数)
```

分母用 `evaluate_split` 返回的 `uids`（就是算 NDCG 的那批人），而不是 `window.active_users`（后者含只训练不评测的用户，可作辅助列）。

**实现**：`dg_run.py` 在评测后取 `uids` 与 `graph` 的 `mask` 求交（几行代码）；per arm × per eval 写一列。与 `n_edges` 并列报告。

**注意**：现有 raw 无法补算（没存逐用户边集），所以它必须列入 §7 阶段 2 的重跑批次。

### 4.1 B1：15 个「独立样本」不成立；应改为「种子为统计单位」

1. 主检验 = 种子级配对差（每种子一个数，n=种子数）；
2. 窗口级（n=15）降级为"敏感性分析/一致性检查"，只报方向与正号比例；
