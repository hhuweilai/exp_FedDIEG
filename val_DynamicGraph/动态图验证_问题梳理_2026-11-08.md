## 3. 归因类问题（A）

### 3.1 A1：`dynamic−static` 的差值里混着「覆盖」——不能全部归因于动态演化

**原文表述**：StaticGraph 只覆盖部分早期用户、DynamicGraph 逐渐覆盖所有用户，所以两者差异不一定来自已有用户关系的动态调整。

**核实：成立，而且比原文说的更强。** 结果如下（seed 42，评测轮上的「有边用户数」）：

| ML-1M 轮次 | 30 | 60 | 120 | 150 | 250 | 390 | 510 | 600 |
|---|---|---|---|---|---|---|---|---|
| static（第 21 轮冻结） | 1264 | 1264 | 1264 | 1264 | 1264 | 1264 | 1264 | **1264** |
| static_at120 | 1366 | 1426 | 1429 | 1429 | 1429 | 1429 | 1429 | **1429** |
| periodic（每 120 轮重建） | 1264 | 1264 | 1264 | 2525 | 2525 | 5261 | 5972 | **5972** |
| dynamic（每轮 EMA） | 1366 | 1426 | 1429 | 2615 | 3599 | 5345 | 6013 | **6040** |

Amazon-Digital-Music 同型：static 冻结在 **2906**，periodic 阶梯 2906 → 6010 → 8542 → 10626 → 12237，dynamic 平滑涨到 **12381**。

**机制（已核到代码）**：

1. `feddieg_core/data.py` 用 `window_mode="slice"`，**每个窗口有自己的活跃用户集**；
2. `FedTrainer.train_round` 只让 `window.has_data(user)` 的客户端训练并上传摘要（`federated.py:213-214`），所以**用户只有在"自己活跃的那个窗口"里才可能进入摘要库**；
3. `graph.update` 的 `update_scope="all"` 只保证"每轮重算全部**已上传**节点"，**不能让没上传的人凭空获得邻居**；
4. 于是 dynamic 的覆盖平台随窗口推进逐级抬升：**1429 → 2664 → 4080 → 5400 → 6040**，**覆盖跳变全部发生在窗口边界（r130 / r250 / r370 / r490）**，窗口内几乎不动。这与「第 1..w 个窗口活跃用户的并集」在数量上完全吻合（机制推断；精确核对方式：拿 `window.active_users` 与「有边用户集合」做差集，应为空）。

**结论**：`dynamic − static` = (①后来窗口的新用户首次获得邻居) + (②已覆盖用户的关系持续重估)。当前实验只证明了这两项之和，**无法把 ② 单独测出来**。这直接影响论文里「动态图演化」的表述。

**处置**：见 A4（`OnboardingOnlyGraph`）。在补上该臂之前，报告里凡是把 ②归因给「动态更新」的句子都要改成「覆盖 + 刷新」的口径（`dg_report.py` 的一句话已经这么写了，但第三章、第五章仍有个别句子需要对齐）。

### 3.2 A2：periodic「5 次刷新拿 67%/82% 收益」——数值可信，但归因与性价比都还没测

**核实**：

- 刷新轮次 = `(r − 20 − 1) % 120 == 0` → **21 / 141 / 261 / 381 / 501**，共 5 次（`dg_common.py:237-238`，`period=120` 默认）。
- 数值：`periodic−nograph` ML **+0.0051**（95%CI [+0.0027, +0.0076]，窗口正号 100%，3/3 种子）；AZ **+0.0142**（[+0.0119, +0.0163]，3/3）。占总收益 67% / 82%。
- 每轮 EMA 相对它的额外边际只有 **+0.0025 / +0.0031**（33% / 18%）。

**但注意两件事**：

1. periodic 的刷新时点（21/141/261/381/501）**落在每个窗口开始后约 20 轮**，其覆盖阶梯恰好在窗口边界后跳一级（1264 → 2525 出现在 r150）。也就是说「5 次刷新」实际测的是「**贴近窗口边界重建一次图**」，不是「刷新频率」这个连续自变量。报告「已知局限 5」已自述"周期只取 120、比例依赖该周期"。
2. **性价比目前没有任何耗时数据**：`dg_run.py` 的 `round_seconds` 把图更新算在 `train_seconds` 里，没有单独计时；只有 `feddieg_core/bench_graph.py` 的离线基准（N=6040、K=20、pool=160 时约 **23 ms/轮**，对 ~2.45 s/轮 的总轮时占比 <2%）。所以"每轮更新是否必要"目前只能从**效果**回答，不能从**成本**回答。

**处置（属新增实验，非本文执行范围）**：`--refresh-rounds` 已存在，可直接扫 `period ∈ {10, 20, 60, 120, 600(=static)}` × 2 数据集 × 3 种子；同时在 `dg_run.py` 里把 `graph.update` 单独计时，报告「NDCG vs 刷新频率 vs 每轮图更新耗时」。先验预期（待证）：图更新耗时占比很小，所以"少刷新"的价值在**结构质量**而非算力。

### 3.3 A3：`static_at120` 名不副实；Amazon 缺该臂

**原文表述**：static_at120 实际是第 21–120 轮持续更新后再冻结，不是第 120 轮才构图一次，需要改名或改实现。

**核实：成立。** `dg_common.py:235-236` 的 `should_update` 为 `r <= freeze_round`，所以第 21–120 轮**每轮都更新**；`graph_updates=100`（见 `dg_arm_summary.csv` 与 raw `dg_summary.csv`）。覆盖轨迹也印证：1366 → 1429 是"边更新边覆盖"，不是"一次建图"。

**两个可选口径（语义不同，必须二选一写清）**：

- **改名**（推荐，零成本）：`static_upto120` / `static_freeze120`，语义 =「第 21–120 轮持续更新，第 120 轮后冻结」；
- **改实现**：新增"第 120 轮一次性重建后冻结"的臂（第 21–120 轮不更新，120 轮清空重建一次）。这样才能回答"晚建图是否比早建图好"，与现在的 ①b 回答的"晚冻结是否比早冻结好"不是一个问题。

**另**：`static_at120` **只在 ML-1M 上跑过**（Amazon 8 个臂里没有），所以 `dg_report.py` 的 ①b 行在 Amazon 显示「没有对应结果」。若要在两个数据集上都谈"冻结时点"，需补 Amazon 3 个 run。

### 3.4 A4：`OnboardingOnlyGraph` 的规格（原文第 1 条建议的落地设计）

**目的**：把「新用户首次获得邻居」（覆盖）与「已覆盖用户的邻居持续重估」（演化）分开，给出三项分解：

```
③ dynamic − nograph  =  ① static − nograph          （有图 vs 无图）
                     +  (onboarding − static)         （新用户覆盖的收益）
                     +  (dynamic − onboarding)        （已覆盖用户关系持续演化的收益）
```

**定义（建议）**：每一轮，只对**当前还没有任何邻居行**的用户建一次边（其摘要此刻可用）；一旦某用户有了邻居，其邻居集合与边权**不再更新**。其余协议（训练、FedAvg、评测、参与序列、负样本流）与动态臂完全一致。

**实现钩子（最小改动，不动 `feddieg_core`）**：

- `dg_common.py`：`ARM_CHOICES` / `ARM_LABELS` / `ARM_SHORT` / `arm_dir_name` 增加 `onboarding`；`PolicyGraph.should_update` 对该臂返回"需要扫描"；
- `PolicyGraph.update`：把 `update_users` 过滤成 `mask.sum(dim=1)==0` 的行（即"尚无邻居"的用户），其余逻辑完全走基类；
- `n_updates` 的语义改为「至少有一个用户首次建边的轮数」，`dg_aggregate.py` 的 hygiene「预热后每轮都更新」只对 dynamic 生效（现在已按臂名前缀判断，需确认 `onboarding` 不被误判）；
- 同时保留 **`graph_update_scope="all"`**：否则窗口外的新用户永远扫不到。

**验收断言（需加进 `dg_selfcheck.py` / `dg_hygiene.csv`）**：

1. NoGraph 的 `delta_rel_max` 仍恒为 0；
2. onboarding 用户**建边后签名不再变化**（逐用户记录首次建边轮次，之后 `edge_signature` 逐位不变）；
3. onboarding 的最终覆盖 ≈ dynamic（ML 应达 6040；若显著更低，说明"建过一次就不再更新"的扫描逻辑有漏洞，比如用户在有邻居之前从未进入过活跃集）；
4. 同一 (数据集, 种子) 下三条臂的负样本流、评测用户、参与序列仍逐位相同。

**成本**：2 数据集 × 3 种子 = **6 个 run**（3090、4 并发约 40 min）；若直接上 5 种子则 10 个 run。

**预期读法**（写进报告，避免事后解释）：

| 结果 | 含义 |
|---|---|
| onboarding ≈ dynamic | ② 的收益几乎全部来自**覆盖**，「每轮 EMA」可省 → 第二阶段该做"谁来建边/何时建边"，不是 ρ 自适应 |
| dynamic > onboarding 且差距 ≈ ⑤(+0.0025/+0.0031) | 关系演化的真实价值就等于现有 ⑤ 的边际 → 与 periodic 结论互相印证 |
| onboarding ≈ static | 覆盖不是主因，"刷新"另有来源（新鲜度/边权质量）→ 需要重新归因 |

## 4. 统计类问题（B）

### 4.1 B1：15 个「独立样本」不成立；应改为「种子为统计单位」

**核实：成立。** `dg_aggregate.py:309-345`（`summarise_contrasts`）把每个 `(种子, 窗口)` 的配对差当成一条观测：`n_obs=15`，bootstrap CI 与 `paired_p` 都在这 15 条上算。而 5 个窗口是**同一次训练轨迹的连续切段**（同一份参与序列、同一批初始参数、模型状态前后相连），窗口之间正相关，`n=15` 会低估方差。

**现有产物已经能做种子级检验**：`tables/dg_contrasts_by_seed.csv` 给出每个种子的 Δ（每种子 5 窗口均值），`dg_contrasts.csv` 里也有 `seeds_positive / seeds_total`。所以：

- **不需要重新训练**就能给出 n=3 的种子级配对差、CI 与符号一致性；
- 但 **n=3 的检验功效很弱**（符号检验最小可达 p=0.25），要写"p<0.05"就必须 5 个种子（B2）。

**处置（报告口径）**：

1. 主检验 = 种子级配对差（每种子一个数，n=种子数）；
2. 窗口级（n=15）降级为"敏感性分析/一致性检查"，只报方向与正号比例；
3. 逐用户配对（`dg_user_paired.csv`，n≈2.4 万–7.6 万）**只能当方向性证据**：同一个用户跨窗口不是独立观测，且 NDCG@10 极稀疏（ΔNDCG>0 只占 12.8%），p=1e-150 这种数字不能当效应量证据（报告「已知局限 4」已自述，需升级为正文口径）；
4. 顺带检查：判定阈值 `|Δ| ≥ 0.006 = 明确`、`0.002～0.006 = 小`（`dg_aggregate.py:448-462` 的 `classify`）是人为设定的，报告里应说明依据，或改用「效应量 + CI + 种子一致性」三元判据。

## 5. 记录与指标口径（C）

### 5.1 C1：periodic / static 的 ECR 恒为 0 —— 记录时点问题，不是「图没变」

**原文表述**：周期图在第 21、141、261 等轮更新，而程序每 10 轮才记录一次指标，更新发生的轮次被跳过，最终 ECR 一直记录为 0。

**核实：完全成立，而且波及的臂比原文说的更多。**

- 每轮都调用 `graph.update()`（`dg_run.py:262-264`），但**只有评测轮才会写 `round_rows`**（`dg_run.py:267-271` 的 `should_eval` + `continue`），`ecr_all` 取的是**本轮** `gstats`（`dg_run.py:349`）；
- 评测轮 = 10 的倍数（`config.py:88`，`eval_every=10`）；periodic 更新轮 = 21/141/261/381/501 → **永远不重合**；
- 实测（ML-1M seed 42，60 个评测行）：`static` **0/60 非零**、`periodic` **0/60 非零**、`static_at120` 10/60 非零（因为它在 30–120 轮每轮都更新）、`dynamic` 58/60 非零；
- `added_mean`（新边数）同样是 0/60 —— 同一原因，**不能拿它论证"静态图没有新边"**；
- 但 periodic 的图**确实变了**：`graph_edge_sig` 在 r150 变号、`graph_n_edges` 1264 → 2525。也就是说"ECR=0"纯粹是记录缺失。

**影响面**：**不影响模型训练、不影响图更新、不影响 NDCG**；只影响结构指标的可读性。问题二（冻结归因）的 ECR 数字全部来自"每轮都更新"的变体，因此**结论不受影响**；受影响的只有 `dg_arm_summary.csv` / 报告里 periodic、static 的 ECR 列。

**两种修法**（原文已给出，建议同时做）：

- (a) **每轮落盘**：把 `dg_round_metrics.csv` 拆成「每轮图指标行」与「评测指标行」，或新增 `dg_graph_round_metrics.csv`（`global_round, ecr_all, added_mean, n_edges, n_updates`）。改动只在 `dg_run.py` 的记录层，**不改任何数值**；
- (b) **评测间隔累计**：记录「两次评测之间新增/变化的边数」，与 (a) 互为校验。

**能否复用日志**：❌ 不能。非评测轮的 `gstats` 从未落盘，raw 里只留了 `graph_edge_sig` 的哈希（只能判断"变了/没变"，给不出变化率），邻居 id 集合也没有保存（`dg_probe_metrics.csv` 只有 `delta_rel / neighbor_cos / has_edge`）。因此 **C1 必须重跑**才能得到正确 ECR；好在它不改数值，可先用 1 个种子做回归、确认 NDCG 逐位一致后再批量重跑。

### 5.2 C2：`frozen_share` 的分母、「均值 vs 末值」、以及「永久冻结」的措辞

**原文表述**：frozen_share 只统计参考时刻和当前时刻都有有效邻居的用户，不能直接解释为全体用户的冻结比例。

**核实：成立。** `dg_common.py:763-789`：

```python
both = ref_valid & cur_valid          # 参考时刻与当前时刻都有邻居的用户
... frozen_share = (turnover < 0.01).mean()   # 仅在这批用户里算
coverage_gain = int((cur_valid & ~ref_valid).sum())  # 补集：新获得邻居的用户数
```

量化（ML-1M seed 42、`dynamic_rho0.8`）：参考快照在第 30 轮，`freeze_ref_n = 1366`（**仅占 6040 的 22.6%**），`coverage_gain = 4674`（**77.4%**）。也就是 `frozen_share` 的分母从一开始就只有全体用户的 1/5，而新覆盖的 4674 人**永远不进这个分母**。Amazon：`ref_n = 3120 / 12381`（25.2%），`coverage_gain = 9261`。

**另一个必须修正的点：「永久冻结」是过强的表述。** 实测 `topk_zero`（ML-1M seed 42）的 `frozen_share` 轨迹是**单调下降**：第 30 轮 1.000 → 第 120 轮 0.828 → 第 600 轮 **0.116**（3 个种子 0.060 / 0.116 / 0.133），`turnover` 从 0 升到 **0.345**；Amazon 更明显：均值 0.134、**末值 0.000（3 个种子全部为 0）**、末轮 `turnover` 0.777–0.835。报告里的 0.48 / 0.19 是**跨评测点的均值**，既不等于末值，也不等于"每个用户永久不变"。

**处置**：

1. 报三个数：**均值 / 末值 / 逐轮轨迹**（后两个 raw 里都有，无需重训）；
2. 分母写清：「在参考时刻已有邻居的 1366 人里……（占全体用户 22.6%）」；
3. 机制句把「永久冻结」改成「**近乎不更新**」：ML 新边 0.04 条/轮、末轮仍有 6%–13% 的用户邻居集一位未变；Amazon 末轮已无冻结用户（数据集差异要写明）；
4. 顺带：报告里的 ⑤（ρ 0.2→0.8）之所以用 ECR 代替 turnover，是因为 **ρ=0.2 的参照格（`dynamic` 臂）早于 `turnover_from_ref` 列加入**，其 raw 里根本没有该列（见 B4）——要么补跑参照格，要么在报告里注明"参照格缺列"。

### 5.3 C3：兴趣相似性 —— 只能说「群体幅度有关」，不能说「个体可预测」，也没能跨数据集复现

**核实（原文第 3 条与第四条第 2 点都与产物一致）**：

| 证据 | 值 |
|---|---|
| 邻居的 genre 相似度 vs 随机基线 | 0.789 vs 0.736 → **lift 1.082** |
| 服务器语义相似度 lift（对照） | **3.250** |
| `corr(genre_diff, sem_diff)` | Spearman **0.368**（只是弱相关：学到的相似度大部分不是 genre） |
| `corr(ΔNDCG, genre_diff)` | Spearman **0.017**（p=0.008，n=23688，个体层面极弱） |
| ΔNDCG 按 genre_diff 五分位 | Q1 0.0050 → Q5 0.0167（**+0.0117**，接近全样本均值 0.0108） |
| ΔNDCG 按兴趣漂移五分位 | Q1 0.0134 → Q5 0.0264（+0.0130） |
| 无标签复核（邻居质量 Q1→Q5） | ML **+0.0183**；Amazon **−0.0015**（不可复现） |

**正确表述**（与 `dg_report.py` 在 `00860d6` 的改写一致）：genre 对齐能解释**收益幅度的一部分**，但**预测不了单个用户**；且这个梯度**不能跨数据集复现**。因此既不能写「兴趣相似 ⇒ 协同有效」，也不能写「邻居越像自己 ⇒ 收益越高」。`dg_report.py` 已按此改写，剩下的工作只是把第三章/第五章里残留的旧措辞对齐。
